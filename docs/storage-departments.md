# Хранилища подразделений и диагностика проверки диска

Обновление от 03.11.2026. Требует установленного первого обновления «Управление диском». Не заменяет отдельное исправление доступа УПТС и страницу «О программе».

## Ошибки 503 и 429

503 в первом запросе означает, что сервер не смог выполнить служебную проверку. По одному скриншоту нельзя отличить отсутствие команды, запрет sudo, неверные права файла и ошибку выполнения Python. Наиболее вероятная причина после установки только исходников — пропущенный шаг установки служебной команды и sudoers.

429 в последующих запросах — ограничение частоты. В первоначальной версии оно включалось на минуту даже после неудачного запуска и затрудняло поиск исходной ошибки.

Обновление проверяет наличие и права служебной команды, различает запрет sudo и ошибку выполнения. Кнопка блокируется на период ожидания и показывает обратный отсчёт, исходная ошибка остаётся видимой. Успешные проверки — не чаще раза в минуту; после ошибки — пауза 10 секунд. Установочная диагностика не запускает sudo автоматически.

На сервере после получения актуальных исходников:

```bash
cd /var/www/html/MyPlatform
sudo install -o root -g root -m 0755 deploy/disk/space-disk-report.py /usr/local/sbin/space-disk-report
sudo visudo -cf deploy/disk/space-disk-report.sudoers
```

Только если проверка показала `parsed OK`:

```bash
sudo install -o root -g root -m 0440 deploy/disk/space-disk-report.sudoers /etc/sudoers.d/space-disk-report
sudo visudo -c
sudo -u space -H sudo -n -- /usr/local/sbin/space-disk-report
```

Последняя команда должна вернуть JSON. `busy` означает занятую службу/развёртывание; `partial` — неполную проверку. Если команда завершается с ошибкой, сохраните её текст для диагностики. От пользователя приложения разрешена только эта фиксированная команда без аргументов. Расширять права sudo или запускать Nuxt под root не требуется.

После исправления нажмите «Обновить показатели». HTTP-ошибки могут оставаться в истории DevTools; успешный новый запрос — отдельная запись. Удаление файлов по-прежнему не выполняется.

## Каталоги

В «Каталогах» отображаются лаборатория, диагностика, УПТС и подразделения из существующей таблицы `Department`. Пустые ещё не созданные каталоги отображаются заранее. Откройте каталог и нажмите **«Подготовить каталог»**; для нового документа подразделения каталог также создаётся при первой загрузке. Просмотр списка сам по себе ничего не создаёт.

| Подразделение | Общие документы относительно LAB_FILES_ROOT |
| --- | --- |
| Лабораторный контроль | `lab/` — существующее расположение |
| Диагностика | `diagnostic/` |
| УПТС | `upts/` |
| Другие подразделения | `departments/<ID подразделения>/` |

Идентификатор в пути не меняется при переименовании отдела. Новое активное подразделение появляется после его создания в администрировании и обновления списка. Для базовых отделов учитываются ключи `lab`/`labcontrol`, `diagnostic`/`diagnostics`, `upts`, а также точные названия «Лабораторный контроль», «Диагностика», «УПТС», «Управление подготовки территории строительства».

Общие документы подразделений можно загружать через файловый менеджер: PDF, JPEG, PNG, XLSX до 50 МиБ. Они не требуют привязки к записи лабораторного реестра. Создание папок, переименование, перенос и удаление используют существующий журнал операций и резервные копии. Вкладка «Документы» пока ищет связанные документы реестра лаборатории; общие файлы других отделов доступны в «Каталогах».

Документы договоров диагностики в текущей модели ещё не подключены к карточкам договоров: новый `diagnostic/` — общий каталог отдела, без автоматической привязки файла к договору. Это обозначено в интерфейсе.

## Существующие проекты УПТС

Файлы проектов находятся в `WORK_PROJECT_FILES_ROOT`, по умолчанию — в соседнем с общим корнем каталоге `projects/`. Они не перемещаются, не копируются и не подменяются символическими ссылками.

Внутри каталога подразделения есть блок **«Проекты и договоры подразделения»**: проекты → договоры → файлы. В нём соблюдаются существующие настройки видимости проекта. Показываются общие документы и личные файлы текущего пользователя; чужие личные файлы не раскрываются даже администратору. Скачивание использует существующий защищённый API. Для добавления и изменения документов конкретного проекта используйте карточку проекта.

Проекты УПТС определяются связью с `UptsProject`; другие общие проекты — назначенным подразделением. Групповой проект без назначенного подразделения не приписывается отделу владельца автоматически.

## Объём по отделам

На вкладке «Управление диском» — кнопка **«Рассчитать по отделам»**. Этот расчёт выполняется от имени приложения, без sudo, независимо от службы очистки. Нужны права чтения общих каталогов и хранилища проектов.

Показываются занятые ГиБ, число файлов и процент. Процент — доля учтённого объёма хранилищ, **не всего системного диска**. 1 ГиБ = 1024³ байт.

В расчёт входят:

- общие папки отделов;
- все физически сохранённые файлы их проектов, включая архив, корзину, личные файлы и файлы договоров;
- общие проекты без определённого подразделения — отдельной строкой;
- файлы вне зарегистрированных каталогов и служебные блоки корня — строкой «Не распределено / служебные файлы».

Считаются занятые блоки (`st_blocks`), а не сумма размеров записей в БД. Жёсткие ссылки учитываются один раз в первом найденном каталоге. Символические ссылки не обходятся. Пересекающиеся корни учитываются без повторного суммирования inode. Имена личных файлов в отчёт не попадают.

Системные логи, релизы, PostgreSQL и резервные копии журнала файловых операций вне этих двух корней не входят в разбивку по отделам. Поэтому её сумма обычно меньше общего занятого места на сервере.

Проверка ограничена 20 секундами обхода, 150 000 записей и глубиной 80 каталогов. При достижении лимита, недоступных/исчезнувших файлах или пропущенных ссылках отчёт явно помечается частичным; проценты относятся к проверенной части. Нулевое значение в частичном отчёте не доказывает отсутствие файлов. Это снимок на указанное время, запускаемый вручную, без фонового обхода при каждом открытии страницы.

## Проверки

Проверены API доступа/частоты/диагностики, реальные операции во временных каталогах, подсчёт занятых блоков, жёсткие ссылки, защита от символических ссылок и выхода за корень, неполные отчёты, сохранение старых файловых операций. Отдельный тест на временной PostgreSQL-совместимой базе PGlite проверяет видимость проектов, границы договоров и исключение чужих личных файлов. В Chromium проверены подготовка каталога, загрузка документа отдела, переходы к файлам проектов, две темы, мобильная ширина и обратный отсчёт.

Новых npm-зависимостей и миграций БД нет. Полная production-сборка Nuxt, работа на вашем сервере и фактическая причина первого 503 здесь не проверялись.
