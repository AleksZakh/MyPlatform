# УПТС — пробная версия для Space

Дата: 30 октября 2026 года. Основа: приложенный архив `Space(1).zip`.
Этот пакет содержит **только новые и изменённые файлы**, а не полный проект.

## Что реализовано

- Плитка «Управление подготовки территории строительства» на главном экране.
- Раздел `/departments/upts`: обзор подразделения, выбранного проекта и работы сотрудников.
- Канбан проектов с предварительными состояниями: входящие, в работе, на проверке, передача материалов, завершён.
- Общие для Space проекты, задачи, участники, роли, комментарии и журнал событий. Второго независимого списка задач нет.
- Канбан задач с переносом карточек, таблица, календарь и существующий план по срокам.
- Подключение существующего проекта Space к УПТС без копирования его задач, команды и файлов.
- Реестр объектов: одна общая карточка может участвовать в нескольких проектах. Цель, готовность и задачи учитываются отдельно в каждом проекте.
- Пять независимых направлений готовности: кадастровый учёт, права, ограничения, документы, передача строителям.
- Привязка задачи к конкретному объекту в проекте либо к проекту в целом.
- Предварительные наборы работ по четырём типам проектов. Перед применением можно изменить строки и выбрать объект. Набор создаёт обычные задачи Space без исполнителей и сроков.
- Договоры проекта с реквизитами и отдельными физическими папками.
- Общие и личные файлы проекта/договора, загрузка, скачивание, корзина, восстановление — через существующий защищённый файловый модуль.
- Excel `.xlsx` с шестью листами: параметры, проекты, задачи, сотрудники, объекты, договоры.
- Учебный проект по отдельной кнопке: 3 объекта, 9 задач, 1 договор. Данные условные; исходные файлы не создаются.

## Установка

1. Сохраните текущий исходный код и резервную копию PostgreSQL.
2. Распакуйте содержимое архива в **корень того же проекта Space**, сохранив пути `app/`, `server/`, `shared/`, `prisma/`, `tests/`, `docs/`. Не создавайте дополнительную вложенную папку Space.
3. Используйте обычное окружение приложения с правильным `DATABASE_URL`. Новый раздел использует существующие зависимости; `package.json` и `package-lock.json` не менялись.
4. Проверьте ожидающие миграции и примените их:

```bash
npx prisma migrate status
npx prisma migrate deploy
npx prisma generate
npm run build
```

Новая миграция: `20261030190000_upts_pilot`. Она добавляет четыре таблицы и две nullable-связи в существующие таблицы. Данные диагностов, лаборатории и существующие задачи не переносятся и не удаляются.

Если `migrate status` показывает другие старые ожидающие миграции или расхождение истории, сначала проверьте их обычным способом для вашего проекта. Не используйте `prisma migrate reset` и не заменяйте миграцию командой `db push` на рабочей базе.

5. После успешной сборки перезапустите приложение своим обычным способом. Для уже настроенного PM2 это, например, `pm2 restart space-app --update-env`, выполняемый под тем же системным пользователем и с тем же окружением, что используются сейчас.
6. Откройте главную страницу Space и новую плитку либо маршрут `/departments/upts`.

Для запуска новой версии нужна именно обновлённая схема и повторная генерация Prisma Client. Новые API не будут работать со старым клиентом.

## Файловое хранилище

Используется **существующий** `WORK_PROJECT_FILES_ROOT`. Если переменная не задана, корень вычисляется так же, как до изменения: соседняя папка `projects` относительно `LAB_FILES_ROOT`.

При `LAB_FILES_ROOT=/var/www/uploads-storage/files` это:

```text
/var/www/uploads-storage/projects/<projectId>/shared/
/var/www/uploads-storage/projects/<projectId>/private/<userId>/
/var/www/uploads-storage/projects/<projectId>/contracts/<contractId>/shared/
/var/www/uploads-storage/projects/<projectId>/contracts/<contractId>/private/<userId>/
```

Папка проекта создаётся при создании проекта; папка договора — при сохранении договора. У пользователя, запускающего приложение, должны оставаться права записи в существующий корень проектов. Новая обязательная переменная окружения не требуется.

Физические имена файлов — UUID; исходное имя и связь с документом находятся в PostgreSQL. Это прежнее поведение файлового модуля. Проекты и договоры можно переименовывать без перемещения файлов, поскольку каталоги используют стабильные ID.

На вкладке «Документы» выбирается папка проекта или договора. Общий список файлов проекта в старом интерфейсе показывает его корневые документы; файлы договора открываются через УПТС. Личные файлы видит только их владелец, пока у него есть доступ к проекту.

HTTP-выдача осуществляется через авторизованный API. Не публикуйте этот каталог прямым публичным `alias` nginx. Лимит и таймаут загрузки сохраняются: `WORK_PROJECT_FILE_MAX_BYTES` и текущие ограничения прокси. Без настройки лимит приложения — 100 МиБ на файл.

Миграция старых файлов не требуется. При резервном копировании сохраняйте PostgreSQL вместе с корнем файлов проектов.

## Первый показ сотрудникам

1. Откройте УПТС и нажмите «Создать демопроект». В пустом разделе эта кнопка находится в нижнем вводном блоке; позднее — в разделе «Проекты».
2. Демопроект создаётся **личным** и помечается как учебный. Его владелец — текущий пользователь. Часть задач назначена ему, часть оставлена без исполнителя. Учётные записи вымышленных сотрудников не создаются.
3. Для совместного просмотра измените видимость в настройках: команда либо выбранное подразделение/группа. Для этого нужно существующее разрешение на создание общих проектов. Добавьте коллег через «Команда».
4. Покажите обзор проекта, готовность трёх объектов, задачи и экран сотрудников. Назначьте несколько задач реальным участникам проекта и переключите фильтр исполнителя.
5. Откройте «Задачи → Набор работ», измените примерный состав и выберите объект. Затем назначьте исполнителей и сроки созданным задачам.
6. Создайте договор или откройте учебный. Добавьте тестовый файл в его папку и скачайте его.
7. Сформируйте Excel для всего проекта и отдельно для сотрудника. Сравните количество задач с экраном.
8. После показа переведите учебный проект в архив через существующий раздел Space («Открыть в Space»). Архивные проекты остаются доступны для чтения и отдельного отчёта по переключателю «Архив».

## Правила доступа и расчёта

- УПТС использует `projectWhere`, существующие роли и права Space. Администратор не получает автоматический доступ к чужим личным проектам.
- Владелец и назначенные руководители управляют реквизитами УПТС, готовностью объектов, договорами и наборами работ. Работа исполнителей с задачами и файлами подчиняется прежним правилам.
- Чтобы руководитель отдела видел необходимый портфель, проекты должны быть доступны ему через команду, подразделение или группу. Одна лишь плитка УПТС доступ к данным не расширяет.
- Срез по сотруднику учитывает **основного исполнителя задачи**. Участие в проекте не означает, что все его задачи назначены этому сотруднику.
- Просрочка: незавершённая задача с крайним сроком раньше текущего дня по Москве. Задача со сроком сегодня не просрочена.
- Показатель «Выполнено задач» — количество и доля закрытых задач. Это не процент юридической готовности объекта.
- «Требует внимания» — открытые задачи с заполненным препятствием. Пять показателей объекта задаются отдельно вручную.
- Поиск фильтрует задачи по названию, описанию, проекту и исполнителю. Пустые проекты при поиске/фильтре сотрудника в срез не входят.
- Excel использует те же фильтры проекта, исполнителя, текста и архива. Объекты и договоры включаются целиком для проектов, оставшихся в срезе; это также указано на первом листе отчёта.
- Отчёт содержит только доступные текущему пользователю сведения. Пользовательские строки экспортируются как текст, не как Excel-формулы.
- Состояние проекта «Завершён» задаётся вручную с описанием результата. Оно пока не устанавливает автоматические условия по объектам и не запрещает изменения; для режима только чтения используется существующий архив проекта.
- Создание/изменение проекта, объекта, договора, добавление набора и экспорт отражаются в существующем журнале. Изменение готовности и договора защищено версией записи. Повторная отправка той же операции создания демопроекта, объекта, договора или набора не дублирует данные.

## Границы пробной версии

Это основа для обсуждения с отделом, а не утверждённый производственный регламент.

- Типы проектов, состояния и примеры наборов пока задаются в коде. Набор редактируется перед применением; централизованный редактор сохраняемых шаблонов ещё не реализован.
- Общие сведения объекта вводятся при создании. Редактор в проекте меняет цель, готовность и примечание. Исправление общей карточки объекта с учётом всех связанных проектов — следующий этап.
- Один договор в этой версии принадлежит одному проекту; повторное использование одной карточки договора в нескольких проектах пока не реализовано.
- Передача строителям пока фиксируется состоянием и примечанием: кому, когда и какие материалы переданы. Отдельного акта приёмки и подтверждения получателя нет.
- Диспетчер — рабочая функция существующего владельца/руководителя проекта. Отдельной очереди входящих заявок и отдельной роли доступа нет.
- Нет карты, импорта из Битрикс24, автоматической маршрутизации согласований, трудозатрат и финансового учёта.
- План по срокам используется существующий; зависимости между работами и автоматический пересчёт сроков не добавлены.
- Полный срез ограничен 500 доступными проектами и 10 000 задачами на серверный запрос. При превышении возвращается явная ошибка; данные и Excel не обрезаются молча. Для больших объёмов потребуется развитие загрузки и аналитики.
- Файловые и SQL-операции не образуют общую транзакцию: при ошибке создания записи может остаться пустая папка. При неопределённом результате записи загруженные байты сохраняются согласно прежней политике файлового модуля.

## Выполненные проверки

- Валидация обновлённой Prisma-схемы и генерация клиента.
- Применение новой SQL-миграции к исходной схеме архива на изолированном PostgreSQL-совместимом стенде PGlite.
- Интеграционный сценарий `tests/work/upts.test.ts`: авторизация, отсутствие доступа к чужим данным, роли наблюдателя/исполнителя, повторное создание демо/объекта/набора, общий объект в двух проектах, независимая готовность, конфликт версий, запрет связи задачи с объектом другого проекта, файловые папки договоров, загрузка/скачивание, экспорт/фильтры, Excel-строки с начальным `=`, архив, журнал.
- Регрессионный сценарий существующего `tests/work/project-files.test.ts`: общие и личные файлы, корзина, доступ по подразделению, отзыв доступа, архивирование во время загрузки, недопустимые имена и символические ссылки.
- Компиляция изменённых Vue-компонентов; отдельная строгая проверка TypeScript с типизированными заменами автоимпортов Nuxt.
- Браузерная проверка фактических Vue-компонентов на тестовых данных: обзор, проект, задачи, сотрудники, объекты, формы проекта/объекта/договора/набора, папка документов; светлая и тёмная темы, ширина 1512 и 390 px. Ошибок JavaScript нет; переполнения всей страницы при 390 px нет.

Полная сборка всего Space, рабочий AD/Kerberos, фактические nginx/PM2 и подключение к вашей PostgreSQL в этой среде не запускались. Их необходимо проверить после установки в вашем окружении. Изолированные проверки не заменяют `npm run build` и проверку прав под реальными учётными записями.

Для повторения интеграционного теста используйте только отдельную пустую тестовую базу с применённой схемой:

```bash
WORK_TEST_DATABASE_URL='postgresql://USER:PASSWORD@HOST/space_work_test?connection_limit=1' \
WORK_PROJECT_FILES_ROOT='/tmp/space-project-files-test-upts' \
node --import tsx --test tests/work/upts.test.ts
```

Тест требует имя базы с окончанием `_work_test` и отдельный путь `space-project-files-test-`. Он не предназначен для рабочей базы.
