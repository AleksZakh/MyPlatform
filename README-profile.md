# Space: личный профиль, 13.10.2026

Изменённые файлы лежат относительно корня проекта. Распакуйте в проект на компьютере разработки, проверьте git diff и отправьте коммит в Git.

## Что изменено
- Профиль прокручивается внутри единственного контейнера; внешний main не прокручивается на /profile. Подвал остаётся на месте. Обёртка обычных страниц растёт по содержимому; административные страницы с собственной прокруткой сохраняют высоту 100%.
- Базовый шрифт профиля .875rem, интервалы и поля компактнее; настройки увеличенного текста через корневой rem сохраняются. Убрана вложенность main в main и красный фон layout.
- Личные данные: псевдоним, контактная и дополнительная электронная почта, телефон, почтовый адрес, о себе.
- ФИО, организация, должность и системная почта доступны для просмотра. Контактная почта не меняет учётные данные, не считается подтверждённой и не используется для восстановления доступа.
- Фото JPEG/PNG/WebP до 5 МБ и 16 мегапикселей. Сервер проверяет содержимое, запрещает анимацию, применяет ориентацию, обрезает по центру до 256×256 и сохраняет JPEG без исходных метаданных. Фото сохраняется сразу, остальные поля — кнопкой.
- Личные данные и фото хранятся в отдельной таблице user_profiles; синхронизация AD их не перезаписывает. Фото доступно владельцу через авторизованный endpoint. Публичного каталога файлов нет, права на хранилище менять не надо.
- Это обновление личного кабинета. Вывод псевдонимов и аватаров в списках чата и карточках других сотрудников пока не добавлен.
- Добавлена прямая зависимость sharp (уже использовавшаяся через обработку изображений). package.json и package-lock.json включены вместе; не заменяйте только один из них. Если после предыдущего архива вы меняли зависимости, перенесите добавление sharp через npm install sharp@0.35.5, сохранив собственные изменения.

Интеграционный тест на изолированном PostgreSQL-совместимом PGlite проверил HTTP endpoints: сохранение, запрет изменения чужого профиля через payload, изоляцию пользователей, блокировку неактивных, обязательный заголовок мутации, валидацию email, загрузку/чтение/удаление фото, отклонение SVG, превышения 5 МБ и 16 Мп, неизменность учётной почты и updatedAt. ## Компьютер разработки
1. Остановите dev-процесс, перенесите файлы и выполните npm ci.
2. Проверьте, что DATABASE_URL указывает на предназначенную для разработки БД. Секреты никуда не присылайте.
3. Для этой БД выполните npx prisma migrate status, затем npx prisma migrate deploy, затем npx prisma generate.
4. Перезапустите dev-процесс. Генерация Prisma при уже работающем процессе недостаточна: в памяти может остаться старый экземпляр клиента.
5. Проверьте профиль при небольшой высоте окна, масштабировании 125–150%, светлой/тёмной теме; подвал должен оставаться видимым, страница прокручиваться целиком внутри него. Проверьте фото, очистку полей и сохранение после обновления страницы.

## Сервер
После коммита и отправки в Git:

    cd /var/www/html/MyPlatform
    git pull --ff-only
    space-release prepare
    space-release db-status НОВЫЙ_RELEASE_ID

Сделайте резервную копию рабочей БД и выполните:

    space-release migrate НОВЫЙ_RELEASE_ID
    space-release activate НОВЫЙ_RELEASE_ID --db-compatible
    space-release status

Миграция 20261013080000_user_profile_details добавляет таблицу, существующие данные не изменяет. На сервере не нужно отдельно запускать generate перед prepare.

## Ошибка 500 на компьютере разработки
На скриншоте падает GET /api/profile/preferences. Это не доказательство проблемы Kerberos. И пароль AD, и Kerberos в текущем коде вызывают resolveAuthenticatedDomainUser; сессия хранит appUser.id, а профиль и настройки ищутся по этому ID.

Нужно посмотреть ошибку в терминале, где работает Nuxt, в момент открытия профиля. Возможные причины: неприменённая миграция user_preferences в БД разработки, старый Prisma Client, другая БД или ошибка подключения. По скриншоту выбрать одну причину невозможно.

Диагностика на компьютере разработки:

    npx prisma migrate status
    npm ls prisma @prisma/client

Пришлите эти результаты и строки серверной ошибки для /api/profile/preferences. Не присылайте .env, DATABASE_URL, cookie, токены и пароли. При публикации журнала удалите персональные данные и секреты, если они попали в текст ошибки.

Если используется отдельная БД разработки, её настройки пользователя независимы от боевой БД — одинаковый доменный логин сам по себе не синхронизирует две базы. Объединять пользователей по имени или произвольному email для устранения 500 нельзя.

Перечёркнутый https на скриншоте — отдельный вопрос доверия сертификату; сама по себе эта индикация не объясняет серверный ответ 500.
