# Space: контакты и приглашения доменных сотрудников

Обновление подготовлено на основе archive.zip от 12 октября 2026 года. Это архив изменённых файлов, а не полный проект. Групповые чаты в эту поставку не входят: следующий этап, новые участники должны видеть всю историю.

## Что изменено

- Вкладка «Контакты»: активированные пользователи, включая offline, имя, подразделение, статус присутствия. По 50 записей, кнопка «Показать ещё».
- Поиск по имени или логину также находит импортированные в Space доменные записи со статусом PENDING_ACTIVATION. Не выполняет массовый поиск/импорт каталога AD.
- При выборе ожидающего активации сотрудника — отдельное подтверждение отправки приглашения. Диалог и сообщение до активации не создаются.
- Перед отправкой проверяются актуальный объект AD, его доступность и адрес почты. Адрес получателя нельзя задать из браузера.
- Письмо содержит ссылку на /login. Не содержит паролей или токена, который сам выдаёт доступ. Пользователь входит через существующий Kerberos или доменный пароль; проверенная идентичность сопоставляется с objectGUID приглашения.
- Самостоятельная активация разрешена только ожидающей записи с успешно отправленным, действующим приглашением. Приглашение действует 7 дней, используется один раз. Записи BLOCKED/DISABLED автоматически не активируются; отключение в AD запрещает вход.
- Изменение локального профиля после приглашения аннулирует разрешение на самостоятельную активацию. Это в том числе предотвращает повторное использование старого приглашения после административной блокировки и возврата в ожидание. Администратор может активировать запись обычным способом.
- Существующий механизм первого входа совершенно нового доменного пользователя не изменён. Внешняя активация по почтовому токену теперь явно ограничена EXTERNAL.
- Права, группы и отделы при активации импортированной записи не назначаются дополнительно. Отправка и активация регистрируются в audit_logs.
- Ограничения: одному адресату не чаще раза в 24 часа, отправителю не более 20 адресатов в час. Эти ограничения пока константы в invitation-policy.ts и invitations.ts.
- При ошибке/неопределённом результате SMTP повторная отправка также закрыта на 24 часа, а разрешение активации не выдаётся. Это исключает немедленные дубли писем; администратор может проверить SMTP и активировать запись вручную. Успешный ответ SMTP означает приём письма почтовым сервером, а не гарантированную доставку в ящик.

## Установка

1. Сделайте резервную копию БД. Перенесите файлы из архива в исходный проект, сохранив структуру. package.json, package-lock.json и конфигурации PM2 в архиве отсутствуют и не заменяются.
2. Закоммитьте изменённые файлы и доставьте этот коммит в /var/www/html/MyPlatform. Убедитесь, что новые migration.sql и серверные файлы отслеживаются Git; в проекте ранее встречались широкие правила .gitignore. Не копируйте файлы в действующий каталог releases вручную.
3. Проверьте настройки в /etc/space/space.env (значения секретов не публикуйте):

```dotenv
NUXT_SITE_URL=https://space.avtodor-eng.ru
NUXT_SMTP_HOST=mail.corporate.example
NUXT_SMTP_PORT=587
NUXT_SMTP_SECURE=false
NUXT_SMTP_FROM=space@corporate.example
# Если сервер требует аутентификацию:
NUXT_SMTP_USER=...
NUXT_SMTP_PASSWORD=...
```

Подставьте реальные настройки корпоративной почты. SECURE=true используется для прямого TLS (обычно 465); для STARTTLS (обычно 587) — false. Без SMTP приложение продолжит работать, но отправка приглашения завершится понятной ошибкой. Секреты нужны только в серверном env, а не при сборке.

4. На сервере:

```bash
space-release prepare
```

Дождитесь READY и подставьте полученный ID:

```bash
space-release db-status RELEASE_ID
```

Ожидается только 20261012120000_domain_chat_invitations (если предыдущие миграции уже применены). При наличии других ожидающих миграций сначала изучите их. Затем:

```bash
space-release migrate RELEASE_ID
space-release activate RELEASE_ID --db-compatible
space-release status
```

Миграция только добавляет таблицу приглашений и внешние ключи к пользователям. Старые сообщения и учётные записи не переписываются. Код предыдущего релиза совместим с новой таблицей. При переключении предусмотрен короткий перерыв. Если нужен откат кода: `space-release rollback --db-compatible`; таблицу вручную не удаляйте.

## Проверка на сервере

1. Откройте чат → Контакты: должны быть активные пользователи, включая offline; проверьте поиск и «Показать ещё».
2. Найдите заранее импортированного ожидающего доменного сотрудника. Выбор контакта не должен отправлять письмо. Нажмите «Отправить приглашение» и проверьте корпоративный ящик.
3. Под этим сотрудником выполните вход через AD. Статус в Space должен стать ACTIVE, в журнале появится активация. Обновите список контактов (повторно откройте окно), начните обычный диалог.
4. Повторите сценарий для второго тестового сотрудника через другой способ доменного входа (пароль/Kerberos).
5. Убедитесь, что приглашение не позволяет войти отключённому в AD или заблокированному в Space пользователю; что отсутствие почты и недоступность SMTP выводят сообщение, не активируя запись.
6. Проверьте обычный вход ранее активного доменного пользователя, внешнего пользователя и отправку личных сообщений.

## Что проверено при подготовке

- Prisma Client успешно сгенерирован из обновлённой схемы.
- Vue/TypeScript: проверка всех ссылочных проектов vue-tsc -b.
- Изолированная тестовая БД (PGlite, PostgreSQL-совместимая): применение новой миграции к предыдущей схеме, отправка через заглушки LDAP/SMTP, повторная отправка, отказ при отсутствующей почте/отключении AD, запрет активации без отправки, истечение срока, несовпадение идентичности, BLOCKED/DISABLED, изменение профиля, однократность активации, журнал и отсутствие новых индивидуальных прав.
- Клиентский тест: offline-контакты, подтверждение приглашения, выбор ожидающего пользователя без создания диалога, повторная отправка сообщения с тем же clientId, синхронизация и очистка при выходе.
- Реальные SMTP/AD/Kerberos и браузер на корпоративном сервере здесь недоступны. Полная production-сборка должна пройти через space-release prepare. Тесты не отправляли настоящих писем.

Тесты оставлены в tests/chat. invitations.test.ts требует пустую тестовую БД с именем *_chat_test и BASE_SCHEMA_SQL — путь к SQL предыдущей схемы, полученному через prisma migrate diff --from-empty --to-schema-datamodel <previous-schema.prisma> --script. Не запускайте тест на рабочей БД. Клиентский тест требует jsdom (в отдельном тестовом окружении).
