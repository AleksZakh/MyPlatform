# Space — импорт работ с договором, 09.11.2026, редакция 2 (без history)

Пакет подготовлен на основе предоставленного Space.tar.xz. Изменения относятся только к работам с договорами ОДИС. Полный исходный SQL в пакет не включён: используйте dis_dog_works.sql из предоставленного архива 7z.

## Что установлено

В исходном архиве было 68 миграций, включая 20261102150000_diagnostic_contract_works. Вывод пользователя «68 migrations found / Database schema is up to date» согласуется с применением этой миграции. Создание таблицы и импорт старых работ — разные операции. Факт импорта надо проверять PLAN; повторный импорт договоров или сооружений не требуется.

## Что изменено

- Файл читается последовательно, по SQL-операторам: общий лимит 512 МиБ снят. Максимум одного оператора ограничен 128 МиБ символов. Если другая выгрузка содержит более крупный INSERT, скрипт остановится с понятной ошибкой, не обрезая данные.
- Большие SQL-строки разбираются через фрагменты, без посимвольного накопления строки. Поле history исключено из rawData и из контрольной суммы записи по решению пользователя. Остальные исходные поля и legacyId сохраняются. Хеш записи вычисляется в фиксированном порядке полей; изменения только history не считаются изменением задания. Контрольная сумма всего SQL по-прежнему проверяет целостность исходного файла.
- Планирование проходит весь файл до начала записи. Повторные ID, повреждённый SQL и изменения файла останавливают запуск. Не редактируйте исходный SQL во время работы.
- При сравнении с прежними импортами, где history входила в хеш, проверяются сохранённые исходные поля без history. Совпадающие задания пропускаются; существующие rawData и аудит не переписываются.
- Повторный APPLY пропускает уже импортированные записи; изменённые исходные записи и удалённые записи требуют разбора. Запись работы и события аудита остаётся одной транзакцией.
- Добавлена НОВАЯ миграция 20261109150000_diagnostic_contract_work_import_actor. Неизвестные автор и редактор старой работы записываются как NULL; оператор и время импорта — отдельно, importedById/importedAt. Старые миграции и уже существующие записи не переписываются. Если работы уже импортированы старым скриптом, их атрибуцию следует разбирать отдельно по аудиту.
- ANALYZE не загружает Prisma и не подключается к БД. PLAN читает БД, но не пишет в неё. В отчёте отложенных записей сохраняются основные поля; history в отчёт не включается.

## Установка

1. Сохраните резервную копию БД и изменяемых исходников обычным для проекта способом.
2. Распакуйте пакет в корень ~/Projects/MyPlatform, сохраняя каталоги. В пакете только изменённые/добавленные файлы, это не полная копия приложения.
3. prisma/schema.prisma основан на архиве, присланном 09.11.2026. Если после этого вы меняли схему в другом чате, не заменяйте её целиком: в модели DiagnosticContractWork замените createdById Int и updatedById Int на Int? и добавьте importedById Int? и importedAt DateTime?. Остальные модели не менять.
4. В том же окружении и каталоге, где выполняли migrate status:

```bash
npx prisma migrate status
npx prisma migrate deploy
npx prisma generate
```

Теперь должна примениться только новая миграция 20261109150000_diagnostic_contract_work_import_actor (общее число — 69). Если статус показывает другие неожиданные миграции или другую БД, сначала выясните причину. Не используйте migrate reset или db push.

## Ближайший шаг: PLAN

Распакуйте dis_dog_works.7z в ~/TMP. Команда ожидает именно SQL, не 7z.

```bash
npx tsx scripts/import-diagnostic-contract-works.ts \
  --file ~/TMP/dis_dog_works.sql
```

Флаг --apply здесь отсутствует: работы и аудит в БД не записываются. Создаётся отдельный каталог отчёта, путь к report.json выводится в конце. Пришлите итоговый вывод и этот report.json. Каталог отчёта должен быть новым; по умолчанию имя уникально.

PLAN сопоставит договоры по контрагенту, номеру и дате, а библиотеку работ — по шифру. Возможные результаты: CREATE, ALREADY_IMPORTED, NO_UNIQUE_CONTRACT, WORK_NOT_AVAILABLE, SOURCE_CHANGED, DELETED_REQUIRES_REVIEW. Число 5 862 ниже не означает, что столько записей уже можно импортировать: оно относится только к корректности исходных полей.

Если нужно повторить только локальную проверку без БД:

```bash
npx tsx scripts/import-diagnostic-contract-works.ts \
  --file ~/TMP/dis_dog_works.sql --analyze-only
```

APPLY поддерживается прежними параметрами --apply --actor-id ID; переходить к нему следует после разбора PLAN и проверки активного пользователя. ID 4 автоматически не выбирается.

## Проверенная выгрузка

- Размер SQL: 602 693 629 байт (~574,8 МиБ).
- Всего: 5 938 записей; основные поля прошли проверку у 5 862; 50 тестовых исключены; 26 отложены.
- 26 отложенных: 8 с нарушением порядка дат, 2 с ошибочным годом, 16 с неполными реквизитами договора.
- В числе неполных записей есть «Отпуск», короткие номера и пустые реквизиты. Их нельзя автоматически привязывать к предполагаемым договорам.
- Статусы источника: completed = 3153, unplanned = 2755, scheduled = 3, overdue = 27. Они сохраняются без изменения; неизвестная интерфейсу подпись остаётся исходным кодом.
- Поле history занимает около 600 МБ SQL-текста, отдельные значения около 51 МБ. В новой редакции history не переносится в PostgreSQL; исходная SQL-выгрузка остаётся без изменений.

Откройте docs/diagnostic-contract-works-20261109/deferred-records.html в браузере: там все 26 записей с исходными датами. Полный машинный отчёт — analysis-report.json. Это ANALYZE, а не результат PLAN на вашей БД.

## Проверки и ограничения

Выполнено: полный ANALYZE на исходном SQL вместе с history, 6 автоматических тестов, включая исключение history из rawData/хеша и совместимость сравнения с прежним форматом, сравнение основных полей всех 5 938 записей со старым парсером на технической копии без истории. Тесты:

```bash
npx tsx --test tests/diagnostic-contract-work-stream.test.ts
```

Подключение к вашей PostgreSQL, выполнение новой миграции, prisma generate, общий typecheck/сборка Nuxt и реальный APPLY здесь не выполнялись. Проверка разбора файла выполнена реальным кодом, без имитации Prisma; интеграционные гарантии работы с БД в этой среде не проверены. Запись и аудит должны быть проверены на целевой БД после PLAN; при сбое ранее завершённые транзакции сохраняются, повторный запуск продолжает перенос.

## Если предыдущий пакет уже установлен

Замените файлы из этой редакции. Дополнительной миграции относительно предыдущего пакета нет: используется та же 20261109150000_diagnostic_contract_work_import_actor. Применённую миграцию повторять не требуется. Если она ещё не применялась, выполните команды установки выше. Запустите PLAN заново: хеши строк теперь рассчитываются без history. Существующие записи не очищаются массово.
