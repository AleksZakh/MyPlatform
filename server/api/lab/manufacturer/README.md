# Производители: полный комплект API и порядок проверки

В комплекте **6 заменяемых endpoint и 1 новый общий service**. Можно получить все файлы сразу, но устанавливать и проверять их последовательно.

**Работать сначала в тестовом контуре.** Схема БД, миграции, общие функции авторизации/аудита, другие справочники, файлы документов и импорт CSV этим комплектом не меняются.

## Состав

```text
server/
├── services/lab/
│   └── manufacturer-api.service.ts        ← добавить первым
└── api/lab/manufacturer/
    ├── index.get.ts                       ← заменить
    ├── all.get.ts                         ← заменить
    ├── [id].get.ts                        ← заменить
    ├── index.post.ts                      ← заменить
    ├── [id].put.ts                        ← заменить
    └── [id].delete.ts                     ← заменить
```

В именах `[id]` нужны обычные квадратные скобки, не `%5B`/`%5D`.

`tests/` содержит необязательные изолированные тесты; `review/` — исходники из присланного архива и сравнение. **Файлы из `review/` не копировать в `server/api`.**

## Что проверено по исходникам

Присланный архив содержит ровно шесть endpoint. В нём каждый создавал свой `PrismaClient`; GET и DELETE ещё использовали `Manufacturer.materials`; удаление было физическим. В POST/PUT авторство могло браться из тела запроса. Проверок через общий `requirePermission` и вызовов общего аудита в этих endpoint не было. Это описание самих обработчиков, не утверждение об отсутствии middleware во всём приложении.

Код сверялся со схемой и общими сервисами из ранее присланного `lab-plp-audit.zip`. В этой схеме Manufacturer связан с ReceiptMaterial через `receipts`, а `ReceiptMaterial.manufacturerId` указывает на производителя.

## Общие правила новых обработчиков

- Право на ресурс `lab.manufacturers`: VIEW / CREATE / UPDATE / DELETE соответственно операции. Учётные записи и разрешения комплект не создаёт.
- GET показывает только производителей с `deletedAt: null`. Поиск — по `name` и `note`; порядок при равных значениях стабилизирован по `id`.
- `index.get.ts`: страницы, сортировка, поиск, максимум 100 строк на страницу. `all.get.ts`: все действующие совпадения без пагинации и без лимита 100.
- POST/PUT записывают только пользовательские `name` и `note`; автор/редактор берётся из учётной записи, проверенной сервером. Переданные клиентом id, даты, авторство и вложенные связи не используются.
- Уникальность имени сохраняется в рамках существующего `@unique`: точное имя после trim, включая мягко удалённые строки. Новое создание и обычный PUT ничего не восстанавливают. Семантическое сравнение названий, поиск похожих организаций, нечувствительная к регистру уникальность и объединение дублей здесь НЕ добавляются.
- При PUT не переданное `note` сохраняется; `note: null`, пустая или пробельная строка очищают его. Изменение без реальной разницы не обновляет `editedAt` и не добавляет пустой аудит.
- CREATE/UPDATE/DELETE и успешный аудит сохраняются одной транзакцией. При ошибке аудита транзакция отменяется. Отклонённое создание не даёт успешного CREATE. Отдельный аудит всех бизнес-отказов здесь не добавляется; ACCESS/DENIED остаётся задачей существующего сервиса доступа.
- DELETE мягкий. Повторный DELETE возвращает `alreadyDeleted: true`, не меняя прежнюю дату удаления и не создавая повторный успешный аудит.

### Какие связи блокируют удаление

| Поступление / Реестр | Учитывается в `_count.receipts` и запрещает удаление? |
|---|---|
| Связано с действующей записью Реестра | Да, даже если deletedAt самого поступления заполнен несогласованно |
| Связано с мягко удалённой записью Реестра | Нет, независимо от deletedAt поступления |
| Действующее поступление без записи Реестра | Да — как в уже обновлённом справочнике материалов |
| Мягко удалённое поступление без Реестра | Нет |

Счётчики и DELETE используют один `manufacturerBlockingReceiptWhere` из общего service. Ссылки исторических поступлений при удалении производителя сохраняются.

### Изменение контракта чтения

**Больше нет `_count.materials` и массива `materials` как прямой связи производителя.**

| Endpoint | Ответ |
|---|---|
| GET `/api/lab/manufacturer` | `{ success, data, total, page, pageSize }`; элементы `data` содержат поля производителя и `_count.receipts` |
| GET `/api/lab/manufacturer/all` | `{ success, data: [{ id, name, note }], total }` — прежний минимальный формат |
| GET `/api/lab/manufacturer/:id` | `{ success, data }`; `data._count.receipts` и `data.receipts` — до 10 примеров учитываемых поступлений |
| POST / PUT | `{ success, data, message }` — прежняя оболочка; служебные поля определяет сервер |
| DELETE | `{ success, id, alreadyDeleted, message }` |

В примерах `receipts` возвращаются `id`, `receiptDate`, `materialId`, `material: { id, name }`. Это **поступления**, поэтому один вид материала может встретиться в нескольких примерах. `_count.receipts` — число всех учитываемых поступлений, не число различных материалов и не длина массива из максимум 10 примеров.

Если старая форма обращается к `row._count.materials`, нужно позже изменить её интерфейс на счётчик поступлений (`row._count.receipts`) и правильную подпись. Простая подстановка количества поступлений под подписью «Материалов» была бы неверна. Формы в архиве отсутствуют; актуальную совместимость UI не заявляем. Прямые проверки API позволяют завершить проверку сервера без переделки UI.

## Перед установкой

Сохрани резервную копию **вне рабочих API-папок**, например из корня проекта:

```bash
mkdir -p temp/backups
zip -r "temp/backups/manufacturer-api-$(date +%Y%m%d-%H%M%S).zip" server/api/lab/manufacturer
```

Не оставляй копии с расширением `.ts` рядом с endpoint: они не входят в новый комплект.

Проводить пофайловую установку следует на локальном/тестовом сервере, без одновременной работы других пользователей. Для рабочего развёртывания сначала проверь весь комплект на тестовом контуре, затем замени все семь файлов одной версией.

**До установки нового `[id].delete.ts` удаление не проверять: в исходной версии оно физическое.**

```bash
npx nuxi typecheck > /tmp/manufacturer-typecheck.log 2>&1

grep -E 'server/api/lab/manufacturer/|server/services/lab/manufacturer-api\.service\.ts' /tmp/manufacturer-typecheck.log
```

После каждого шага не должно быть ошибок **в только что заменённом файле и общем service**. До конца замены шести API сообщения из ещё старых файлов ожидаемы. После установки всего комплекта не ожидаем ошибок во всей папке производителей.

Пустой отфильтрованный вывод не доказывает, что весь Nuxt-проект исправен. При ненулевом коде завершения полный лог остаётся в `/tmp/manufacturer-typecheck.log`; там могут быть ошибки других модулей или ошибка запуска самой проверки.

Новые зависимости, `prisma migrate` и `prisma generate` для установки не требуются: схема не менялась.

## Шаг 0 — общий service

Добавь `server/services/lab/manufacturer-api.service.ts`. Он содержит общие правила, но сам не создаёт HTTP-маршрут. На этом шаге проверяем наличие файла и его типы. Ничего в БД не создаём и не удаляем.

## Шаг 1 — index.get.ts

Замени `server/api/lab/manufacturer/index.get.ts`, выполни проверку типов. В авторизованном браузере:

```text
/api/lab/manufacturer?page=1&pageSize=10
/api/lab/manufacturer?page=2&pageSize=10&sortKey=id&sortOrder=asc
```

Ожидается `success: true`, не более 10 элементов на странице, корректные `page`, `pageSize`, `total`. При достаточном числе записей вторая страница содержит другие ID. В каждой строке `_count.receipts`, без `_count.materials`.

Проверь `search` фрагментом известного имени и затем примечания. `total` относится к тому же поиску. Удалённые производители не попадают ни в страницу, ни в total. Без новых изменений данных повторный одинаковый запрос должен давать одинаковый порядок.

## Шаг 2 — all.get.ts

Замени `all.get.ts`, проверь типы, открой:

```text
/api/lab/manufacturer/all
```

Ожидается полный список действующих производителей; `total === data.length`. В элементах только `id`, `name`, `note`. Не привязываемся к прежнему числу 544: тестовые создания/удаления могли его изменить. При одинаковом поиске и неизменившихся данных total совпадает с total первого endpoint.

Производитель без поступлений тоже должен быть доступен для выбора. Старый cache формы может потребовать перезагрузки страницы; сначала оцениваем свежий HTTP-ответ.

## Шаг 3 — [id].get.ts

Замени `[id].get.ts`, проверь типы. Возьми существующий ID из `/all`:

```text
/api/lab/manufacturer/ID
```

Ожидается `success: true`, производитель с этим ID, `_count.receipts`, массив `receipts` длиной от 0 до 10. Счётчик должен совпадать с соответствующей строкой списка при неизменившихся данных. Пустой массив допустим.

Дополнительные чтения:

```text
/api/lab/manufacturer/abc
/api/lab/manufacturer/0
```

Ожидается 400 `INVALID_MANUFACTURER_ID`. Достоверно несуществующий или мягко удалённый ID — 404 `MANUFACTURER_NOT_FOUND`. GET не пишет успешный DATA-аудит.

## Шаг 4 — index.post.ts

Замени `index.post.ts`, проверь типы. Под учёткой с `lab.manufacturers / CREATE` создай **отдельного тестового производителя A**:

```json
{ "name": "ПРОИЗВОДИТЕЛЬ — ТЕСТ API 01", "note": "Проверка полного комплекта API" }
```

Используй новое имя, если это уже занято. POST `/api/lab/manufacturer` должен вернуть `success: true`, данные и новый ID. Сохрани этот ID для следующих шагов. A пока ни с чем не связывай.

Проверь: A есть в обоих списках, GET по ID работает, в журнале есть успешный `CREATE`, `entityType: Manufacturer`, правильные ID и автор.

Повтори создание с тем же именем: 409 `MANUFACTURER_NAME_EXISTS`, нет второй строки и второго успешного CREATE. Пустое/пробельное имя — 400. Имя уже мягко удалённого элемента — 409 `MANUFACTURER_NAME_RESERVED`; старый элемент не восстанавливается.

## Шаг 5 — [id].put.ts

Замени `[id].put.ts`, проверь типы. У действующего A измени только примечание. PUT `/api/lab/manufacturer/ID_A`:

```json
{ "name": "ПРОИЗВОДИТЕЛЬ — ТЕСТ API 01", "note": "Примечание после UPDATE" }
```

Ожидается сохранение, прежний ID, `UPDATE` в журнале с изменением `note`. Повторно сохрани без изменений: успешный ответ «Данные производителя не изменились.», без нового UPDATE и без изменения editedAt.

Затем переименуй A в свободное тестовое имя: прежний ID, изменение `name` в аудите. Попытка присвоить имя другого производителя — 409, прежнее название сохраняется.

Проверка распространения названия — **на тестовом производителе B со связанной тестовой записью Реестра**, не на рабочем элементе сотрудников. Измени название B в справочнике, обнови таблицу Реестра и открой связанную запись заново на просмотр. Новое название должно отобразиться без сохранения самой записи. `receiptMaterial.manufacturerId`, материал, даты поступления/Реестра и десятиминутные окна остаются прежними. После теста верни B исходное имя. Наличие B понадобится для проверки запрета удаления.

Отдельный тест `note` можно выполнить API: отсутствие свойства сохраняет его старое значение; `null` явно очищает. Это не PATCH — `name` в PUT остаётся обязательным.

## Шаг 6 — [id].delete.ts

Замени `[id].delete.ts`, проверь типы. Теперь можно тестировать удаление.

### 6.1. A без связей

Перед удалением убедись, что `_count.receipts` A равен нулю. DELETE `/api/lab/manufacturer/ID_A` под учёткой с DELETE:

- `success: true`, прежний ID, `alreadyDeleted: false`.
- После свежего GET A отсутствует в списке и `/all`; GET по ID возвращает 404.
- В Prisma Studio строка остаётся с заполненными `deletedAt` и `deletedBy`.
- В журнале — один успешный `DELETE` для `Manufacturer` с ID A.

Повтори DELETE того же ID через API: `success: true`, `alreadyDeleted: true`; дата удаления прежняя, второго успешного DELETE нет. Повторный POST имени A — 409 `MANUFACTURER_NAME_RESERVED`. PUT ID_A с новым именем и даже переданным `deletedAt: null` — 404, A не восстанавливается.

### 6.2. B с действующей связью

GET B должен показывать `_count.receipts > 0`. Попытайся удалить его под **той же учёткой с DELETE**, которая удалила A. Ожидается **409 `MANUFACTURER_IN_USE`**, `data.activeReferences > 0` и понятное сообщение. B остаётся действующим; поступления, Реестр и их ссылки не меняются; успешного DELETE в аудите нет.

Заблокированная кнопка без запроса проверяет только UI. Ответ 403 проверяет доступ, а не запрет из-за использования. Для этого теста нужен именно отправленный DELETE и 409.

### 6.3. Только мягко удалённые связанные записи

Этот сценарий выполняется в изолированной тестовой базе, на отдельном производителе C и контролируемых тестовых записях. У C не должно остаться действующего Реестра и отдельных действующих поступлений без Реестра. Если связанный Реестр мягко удалён, эта связь не учитывается: `_count.receipts === 0`, DELETE C разрешён. ID и исторические ссылки поступлений должны сохраниться.

Не удаляй рабочие записи ради этого теста. Если подходящей тестовой ситуации пока нет, отметь сценарий «не проверен», а не «пройден». Восстановление Реестра с удалённым производителем — отдельная будущая задача; этот комплект restore-endpoint не добавляет.

## Как проверить запись API без зависимости от старой формы

Используй авторизованную вкладку приложения. Не переноси пароли, cookie или токены в переписку. В консоли браузера можно определить помощник:

```js
async function manufacturerRequest(method, suffix = '', body) {
  const options = { method, credentials: 'same-origin' };
  if (body !== undefined) {
    options.headers = { 'Content-Type': 'application/json' };
    options.body = JSON.stringify(body);
  }
  const response = await fetch(`/api/lab/manufacturer${suffix}`, options);
  const result = await response.json();
  console.log(response.status, result);
  return { status: response.status, result };
}
```

Он сам ничего не меняет. Вызовы выполняй только с намерением соответствующего теста. Например, в шаге 4:

```js
await manufacturerRequest('POST', '', {
  name: 'ПРОИЗВОДИТЕЛЬ — ТЕСТ API 01',
  note: 'Проверка создания'
});
```

Для PUT/DELETE подставляй **ID своего тестового элемента**, не произвольный ID из примера. До шага 6 DELETE не вызывай. Метод fetch не выбрасывает исключение только из-за HTTP 4xx: смотри напечатанный статус и тело. Во вкладке Network 4xx при отрицательном тесте остаётся корректным ожидаемым ответом.

В Postman нужна авторизация именно нужного пользователя приложения. Нельзя сделать вывод о бизнес-запрете по 401/403. Значения успешного автора/редактора берутся из серверной учётной записи, а не из тела запроса.

## Коды для интерпретации тестов

| Статус / код | Значение |
|---|---|
| 200 | Успешное чтение/создание/изменение/мягкое удаление; сохраняем прежние успешные статусы |
| 400 `INVALID_MANUFACTURER_*` / `INVALID_PAGE` | Некорректные данные запроса |
| 401 | Нет действительной авторизации/не найдена учётная запись |
| 403 | Нет нужного права, пользователь или ресурс недоступны |
| 404 `MANUFACTURER_NOT_FOUND` | Для GET/PUT: элемент не найден или удалён; для DELETE: ID не существует |
| 409 `MANUFACTURER_NAME_EXISTS` | Название занято |
| 409 `MANUFACTURER_NAME_RESERVED` | Название принадлежит мягко удалённому элементу |
| 409 `MANUFACTURER_IN_USE` | Есть препятствующие удалению связи; подробность `data.activeReferences` |
| 409 `MANUFACTURER_STATE_CHANGED` / `MANUFACTURER_CONCURRENT_UPDATE` | Обнаружено конкурентное изменение; обновить данные и повторить |
| 500 `MANUFACTURER_*_FAILED` | Техническая ошибка; детали остаются в серверном логе |

Понятный русский текст находится в `data.message` ответа H3. При работе через `$fetch` это обычно `error.data?.data?.message`; старая форма может вместо него печатать технический FetchError. Это отдельная UI-доработка, не повод менять бизнес-отказ на HTTP 200.

## Автоматические проверки и ограничения

После установки **всех семи файлов** можно запустить:

```bash
node --test tests/manufacturer-api.unit.cjs
```

Требуется уже установленный в проекте TypeScript. Тест загружает реальные исходники новых обработчиков, service и существующий `server/utils/auditLog.ts`, но заменяет Prisma, проверку разрешений и H3 имитациями. Никакая реальная БД/сессия/сеть не используется. Rollback и конфликты P2034 в этих тестах моделируются, а не вызываются настоящим PostgreSQL.

При подготовке комплекта: **76 изолированных тестов прошли**. Отчёт: `tests/TEST_REPORT.md`. Это не полная проверка типов Nuxt и не интеграционный тест с БД пользователя. Обязательны локальные проверки выше.

Есть две границы, которые нельзя скрыть обещанием «все гонки устранены»:

1. PUT защищён от конкурентного изменения после чтения *внутри серверной операции*. Версия записи с момента открытия формы пока не передаётся; защита от сохранения очень старой формы — отдельная задача.
2. DELETE выполняет проверку и мягкое удаление в Serializable-транзакции. Но согласованность с одновременной **привязкой производителя через другие маршруты** зависит и от этих маршрутов. Этот пакет их не меняет. При общем аудите записей/восстановления потребуется проверить повторную проверку доступности и общую схему синхронизации во всех путях записи. Существование внешнего ключа само по себе не проверяет deletedAt.

Не добавлены: восстановление производителя, импорт Excel/CSV, объединение дублей, обновление уже открытых экранов через push и новые поля производителя. Не обновляются другие API, общий auditLog/access-control и схема Prisma.
