# Восстановление отсутствующих протоколов — v3

Архив заменяет v2. Установите ВСЕ пять файлов кода с сохранением каталогов.
Новый файл server/utils/protocol-migration-file.ts нужен обоим эндпоинтам.
shared/utils/migration-document.ts также включён. Новых зависимостей и
миграций схемы БД нет. Существующий protocol-migration.service.ts не меняется.

## Порядок установки

1. Остановите другие экземпляры импорта протоколов.
2. Сохраните резервную копию protocol-state.jsonl и исходного отчёта.
3. Перенесите файлы в проект. Выполните npx nuxt typecheck, обычную сборку
   и перезапустите процесс Space. Проверяйте именно развёрнутый сервер.
4. На компьютере запуска скрипта обновите клиент и shared/utils/migration-document.ts.
5. Используйте тот же полный CSV, журнал, SPACE_BASE_URL и настройки CA,
   что в успешном импорте. Не очищайте пути в БД и не удаляйте файлы.

## Проверка

Из корня проекта:

```bash
DRY_RUN=1 REPAIR_MISSING=1 RECOVER_UNCERTAIN=1 \
RETRY_REPORT=./scripts/import-files/protocol-report-2026-09-30T13-59-07-436Z-392581.jsonl \
CSV_PATH=./legacy-data/testProtocols.csv \
npx tsx scripts/import-files/import-protocols.ts
```

RETRY_REPORT — ИСХОДНЫЙ отчёт полного импорта 30 сентября, с FAILED/UNCERTAIN.
Не подставляйте отчёт проверки 1 октября: в нём другие статусы.
Если ранее PROTOCOL_STATE указывал другой файл, сохраните эту настройку.
Скрипт по умолчанию читает scripts/import-files/protocol-state.jsonl.
Для собственного CA можно использовать NODE_EXTRA_CA_CERTS=/путь/ca.pem.
Команды не отключают проверку TLS.

DRY_RUN читает БД/файлы на Space и создаёт новый отчёт. Документы старого
портала не скачиваются, БД и журнал состояния не изменяются.
READY_TO_REPAIR_MISSING означает предварительную готовность: SHA-256
повторно скачанного документа будет проверена только при реальном импорте.

## Пробное восстановление

После просмотра проверочного отчёта:

```bash
DRY_RUN=0 MAX_FILES=3 REPAIR_MISSING=1 RECOVER_UNCERTAIN=1 \
RETRY_REPORT=./scripts/import-files/protocol-report-2026-09-30T13-59-07-436Z-392581.jsonl \
CSV_PATH=./legacy-data/testProtocols.csv \
npx tsx scripts/import-files/import-protocols.ts
```

Проверьте открытие документов в Space. Для остальных используйте ту же
команду с MAX_FILES=0. MAX_FILES ограничивает попытки скачивания/загрузки,
а не количество сверок уже сохранённых документов.

## Как работает восстановление

- Выбираются только назначения FAILED/UNCERTAIN исходного отчёта.
- По полному CSV проверяются уникальность совпадения и отсутствие нескольких
  разных исходных документов на одну запись.
- Для восстановления заполненного пути нужна история UNCERTAIN и прежняя
  SHA-256 (берётся также из предшествующей записи UPLOAD_PENDING).
- Сервер отличает отсутствие файла/подкаталога (MISSING) от отсутствия
  самого корня хранилища, отказа доступа, неверного формата и иных ошибок.
  Корень LAB_FILES_ROOT должен указывать на то же рабочее хранилище.
- Клиент скачивает документ и сравнивает SHA-256 с журналом первой попытки.
  При различии — SOURCE_HASH_CHANGED и ручная проверка.
- Эндпоинт независимо проверяет SHA-256 принятых байтов относительно
  переданной контрольной суммы, неизменность старого пути и отсутствие файла.
  Исходная историческая сумма хранится на стороне миграционного клиента.
- Новый файл сохраняется под новым уникальным именем. Перед изменением БД
  отсутствие старого файла проверяется повторно. Условное обновление БД
  учитывает старый путь, поля протокола, editedAt и связанный отбор проб.
  При конфликте обновление не выполняется.
- Путь и аудит изменяются в одной транзакции (timeout 30 секунд).
  Нет промежуточного обнуления пути. Старые файлы не удаляются и не перезаписываются.
- При неопределённом результате commit новый файл сохраняется, если БД
  подтверждает ссылку на него либо недоступна для проверки. Следующий запуск
  сверяет фактический файл с журналом по SHA-256.

Символические ссылки в пути проверяемого файла не допускаются; это даёт
UNAVAILABLE и требует ручной проверки. Нераспознанный формат, ошибка чтения
и файл более 50 МиБ также не считаются отсутствием.
Не запускайте одновременно другие работы по перемещению/восстановлению
того же хранилища: транзакция БД не блокирует внешние изменения файловой системы.

## Статусы и счётчики

READY_TO_REPAIR_MISSING — отсутствующий файл готов к попытке восстановления.
READY — обычная загрузка. READY_TO_RETRY — повтор без старого пути в БД.
RECONCILED_SUCCESS — файл уже есть и совпал с журналом; повторного скачивания нет.
ATTACHED_FILE_UNAVAILABLE — поле reason содержит этап/причину проверки.
ATTACHED_FILE_MISSING — отсутствие подтверждено, но не выполнены условия
восстановления (флаги, UNCERTAIN, прежняя SHA-256); детали есть в отчёте.
RECOVERY_PATH_CHANGED — путь изменился после проверки.

success включает успешные новые загрузки и восстановления; ready — предварительную
готовность; reconciled — сверенные неопределённые загрузки; existing — уже имеющиеся
документы; review — ручную проверку; skipped — строки вне набора повторного прохода.
В dry-run RECONCILED_SUCCESS не дописывает SUCCESS в журнал.

Три записи ID 11681, 11813, 11829 с номерами-заглушками остаются исключёнными.
Успешные назначения исходного импорта и его неоднозначные совпадения не выбираются.

## Проверено

Проверка типов клиента/серверных файлов в изолированном окружении пройдена.
Тесты проверили реальное определение наличия/отсутствия файла, недоступный корень,
ошибку доступа, символические ссылки и неверное содержимое; клиентский dry-run,
восстановление по старому пути и SHA-256, блокирование изменившегося документа;
серверную проверку хэша/пути, запрет замены существующего файла и обработку
ошибок транзакции. HTTP и БД в тестах имитировались; на боевой БД патч не запускался.
