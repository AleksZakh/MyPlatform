# Space: компактный AdminCenter, группы AD и диагностика Kerberos

Обновление поверх `space-access-management-v1.zip`. Подготовлено по ранее переданному проекту и пакетам; ваш запущенный сервер и его конфигурация nginx не были доступны.

## Что изменилось

- Верх AdminCenter уплотнён: компактный заголовок и индикатор AD, статистика в одну строку на desktop.
- В правах сотрудника и подразделения прокручивается таблица. Заголовок карточки, вкладки, фильтры и счётчики остаются на месте. Заголовки столбцов закреплены.
- Кнопка «Доменные группы» открывает `/admin/access?kind=domainGroup`. Можно найти группу безопасности в AD, добавить в Space и назначить права общей матрицей. В личных правах сотрудника видны названия групп, дающих доступ.
- Для Kerberos добавлены повторный доменный вход, понятный этап ошибки, идентификатор запроса и безопасные диагностические записи. Исправлено расположение параметров сессии Nuxt.

**Подразделение AD (атрибут department) и доменная группа — разные сущности.** В v1 была только выдача сотрудникам и подразделениям; теперь есть отдельные DomainGroup / DomainGroupPermission.

## Установка

Новая серверная часть требует две новые таблицы. Перед переключением приложения подготовьте миграцию и Prisma Client в вашей обычной процедуре обновления. Сделайте резервную копию БД и изменяемых файлов. Если после v1 вы самостоятельно меняли эти файлы, используйте `changes-from-v1.patch` для сверки.

1. Скопируйте из пакета `app/`, `server/`, `shared/`, `prisma/patches/`, новый каталог `prisma/migrations/20260922140000_domain_group_permissions/` и `scripts/apply-domain-groups-schema.mjs` в проект с сохранением путей.
2. Добавьте модели в вашу текущую схему, не заменяя её целиком:

```bash
node scripts/apply-domain-groups-schema.mjs
npx prisma validate
npx prisma migrate status
```

Скрипт добавляет только связь в AccessResource и две модели. Он сохраняет рядом резервную копию схемы и останавливается при частично добавленных моделях. Если ваша схема уже содержит дубли моделей или незаполненные `@relation(...)`, сначала устраните их: скрипт их не исправляет. Вручную те же изменения описаны в `prisma/patches/domain-groups.prisma`.

3. После проверки списка ожидающих миграций выполните в нужном окружении:

```bash
npx prisma migrate deploy
npx prisma generate
```

SQL новой миграции создаёт только `domain_groups`, `domain_group_permissions` и их индексы/связи; существующие данные не переписывает. Не используйте `migrate reset`. Если ваш проект ещё не ведёт историю Prisma migrations, сначала согласуйте её с реальной БД; не отмечайте неизвестные миграции выполненными ради обхода ошибки.

4. Вручную объедините изменения `config/nuxt-config.patch` с вашим `nuxt.config.ts`. Полный config намеренно не заменяется. Нужно добавить `runtimeConfig.ad.groupsBaseDN: ''` и перенести параметры сессии в `runtimeConfig.session`. Подробности ниже.
5. Задайте на сервере, например:

```dotenv
NUXT_AD_GROUPS_BASE_DN=OU=Groups,DC=corp,DC=example,DC=ru
```

В качестве области можно указать корень нужного домена, если группы расположены в разных OU. Сервисной учётной записи AD нужен доступ на чтение этих групп и членства. Область пользователей (`ad.baseDN`) остаётся прежней. Не помещайте сервисный пароль в `runtimeConfig.public`.

6. Проверьте стабильный **существующий** `NUXT_SESSION_PASSWORD` (не менее 32 символов) в runtime-окружении всех экземпляров сервера. Не меняйте рабочий секрет ради установки этого пакета. Разные секреты на экземплярах или его смена делают прежние cookie непригодными.
7. Выполните `npx nuxi typecheck`, обычную сборку `npm run build` и перезапуск приложения. Затем откройте AdminCenter как активный системный администратор из `NUXT_ADMIN_LOGINS`.

Новых production-зависимостей нет. Используются ваши Prisma, h3, Vue, activedirectory2 и nuxt-auth-utils.

## Назначение группе

1. AdminCenter → «Доменные группы» → «Добавить группу из AD».
2. Введите не менее двух символов; выберите группу по названию и DN. При одинаковых названиях сверяйте OU и objectGUID.
3. Нажмите «Добавить и назначить права», затем включите нужные операции.
4. Откройте права сотрудника — под соответствующей операцией появится «Группы AD: …».

Добавление группы само по себе не выдаёт доступ. Каждый флажок сохраняется сразу; аудит и назначение записываются в одной транзакции. Управление доступно только активному системному администратору. Членство в группе не даёт возможности раздавать полномочия.

## Как вычисляется доступ

Активный сотрудник получает объединение личных прав, прав активного подразделения и прав зарегистрированных групп безопасности AD. Неактивный ресурс или заблокированный пользователь не получают доступ. Снятие личного флажка не отменяет право, полученное из группы или отдела: источник виден под операцией.

Группа связана с AD через objectGUID; её переименование не переносит права другому объекту. Данные для регистрации группы повторно читаются на сервере: имя и членство из браузера не принимаются. Пользователь проверяется через ту же локальную связь с AD, что используется при входе; автоматической перепривязки учётных записей нет.

Проверка членства выполняется сервером при запросе, которому требуется групповое право. Между запросами членство не кэшируется; в рамках одного запроса повторные чтения объединяются. Отзыв группового назначения в Space виден следующему запросу. Изменение членства в AD видимо после того, как его отражает используемый контроллер (с учётом репликации AD).

Если AD недоступен, неподтверждённое групповое право не выдаётся: API возвращает 503 с `AD_GROUP_ACCESS_UNVERIFIED`, а матрица показывает предупреждение. Личные права и права подразделения продолжают проверяться через БД. В успешном ответе guard перечисляет источники, достаточные для решения; полная матрица дополнительно проверяет AD.

Поддерживаются вложенные членства по связям `member` в настроенной области одного домена. **Основная группа пользователя (`primaryGroupID`, часто Domain Users), distribution groups и межлесные членства в этой версии не используются как роли.** Для Space создавайте отдельные группы безопасности с обычным членством. Точная проверка областей и вложенности в вашем AD нужна после установки.

## Сессия Nuxt

Для установленного nuxt-auth-utils 0.5.29 `auth.cookieName`, `auth.maxAge`, `auth.csrf` не являются поддерживаемой конфигурацией cookie. Используется `runtimeConfig.session`. В patch сохранено фактическое стандартное имя `nuxt-session`, а не ранее неработавшее `userSession`. Если вы отдельно уже настроили другое рабочее имя cookie, сохраните его. Удаление неподдерживаемого `auth.csrf` не заменяет защиту endpoint: изменения прав по-прежнему требуют JSON, специального заголовка и отклоняют cross-site запросы.

Источник: [код nuxt-auth-utils 0.5.29](https://github.com/atinux/nuxt-auth-utils/blob/v0.5.29/src/module.ts).

## Kerberos

Начните с `docs/KERBEROS-DIAGNOSTICS.md`. Исправление причины повторного ввода пароля требует результата запроса на вашем сервере. В пакете нет утверждения, что SPNEGO/nginx уже починен.

## Проверки и возврат

Подробности — `docs/TEST-RESULTS.md`; снимки полного компонента AdminCenter — рядом. Это проверки кода в изолированной среде, не проверка вашего домена и nginx.

Для отката можно вернуть предыдущие файлы приложения и config. Старый код v1 игнорирует новые таблицы; удалять их для отката не требуется. Новые назначения групп перестанут учитываться после возврата старого guard. Полную резервную схему используйте только если с момента обновления не было других изменений.
