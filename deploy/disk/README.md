# Управление диском в Space

Вкладка: **Администрирование → Файловое хранилище → Управление диском**.
Это проверка с отчётом. Удаление, очистка логов, перезапуск служб и фоновые задания из веб-интерфейса не выполняются.

## Установка служебной команды на сервере

Сначала перенесите обновление в исходники, закоммитьте и доставьте его на сервер обычным способом. Следующие команды выполняются в **актуальном каталоге исходников** сервера, после завершения текущей очистки:

```bash
cd /var/www/html/MyPlatform

sudo install -o root -g root -m 0755 \
  deploy/disk/space-disk-report.py \
  /usr/local/sbin/space-disk-report

sudo visudo -cf deploy/disk/space-disk-report.sudoers
```

Если проверка показала `parsed OK`, установите правило:

```bash
sudo install -o root -g root -m 0440 \
  deploy/disk/space-disk-report.sudoers \
  /etc/sudoers.d/space-disk-report

sudo visudo -c
```

Правило разрешает только пользователю **space** запускать одну фиксированную root-команду **без аргументов**. Оно не разрешает запуск произвольного Python, shell, rm или команд очистки. Python запускается с `-I` и не использует PYTHONPATH/модули из текущего каталога. Не выдавайте права на изменение `/usr/local/sbin/space-disk-report` пользователю приложения.

Проверка установки:

```bash
sudo -u space -H sudo -n -- /usr/local/sbin/space-disk-report
```

Команда выдаёт JSON-отчёт. Если выполняется prepare/activate или ручная очистка, нормальный результат — `status: busy`. Если получен `partial`, посмотрите `warnings`: отсутствие нужных метаданных не считается доказательством, что релиз можно удалить.

Затем подготовьте и активируйте новый релиз обычным способом через `space-release`. Для этого обновления **не нужны миграции БД и npm-зависимости**. Само приложение продолжает работать от `space`; запускать Nuxt под root не требуется.

## Что показывает вкладка

- Общий объём, занятое место, доступное приложению место и резерв файловой системы; отдельно — свободные inode. Порог предупреждения — 90% заполнения и менее 5% свободных inode.
- `/`, каталог релизов и настроенное файловое хранилище (`LAB_FILES_ROOT`) проверяются через `statfs`. Пути на одном устройстве объединяются, объём не суммируется повторно. Показатели относятся к файловой системе, не к размеру указанного каталога.
- Кнопка запускает проверку релизов `/var/www/space/releases` и файлов непосредственно в `/var/log/space` и `/home/space/.pm2/logs`.
- Сохраняются версии из `current`, `deployment.json` (текущая, предыдущая и конфигурация предыдущих процессов), сохранённого списка PM2 и его backup, версии из путей процессов и открытых файлов. Также сохраняются три последних каталога релизов по имени с UTC-меткой времени.
- Кандидаты среди логов: обычные файлы с именами ротации, старше 30 суток по mtime, без открытых дескрипторов и дополнительных жёстких ссылок. Поддержаны `.log.1`, `.log.2.gz`, `.log-YYYYMMDD.gz`, датированные `.log` и формат pm2-logrotate с `__YYYY-MM-DD`. Обычные `combined.log` и `error.log` сохраняются независимо от возраста.
- Размер считается по выделенным блокам. Жёсткие ссылки не включаются в оценку освобождения; поэтому она консервативная. Для сохраняемых релизов полный размер не вычисляется, чтобы не тратить время проверки на защищённые деревья.

Оценка — снимок на момент проверки. Отчёт не является разрешением удалить пути позже без повторной проверки процессов и состояния развёртывания.

## Ограничения и защита

- API проверяет действующего активного пользователя по БД и системную роль администратора. Клиент не передаёт пути, shell-команды или параметры root-процесса. Вызов сделан через execFile с фиксированными аргументами, без shell.
- Запрос проверки записывается в существующий журнал событий как `DISK_SCAN_REQUEST`. Содержимое логов, секреты окружения и дампы PM2 в журнал и браузер не передаются.
- Используется тот же `deploy.lock`, что в space-release и скрипте ручной очистки. При незавершённом переключении проверка откладывается. Отдельная блокировка исключает одновременные проверки из разных процессов приложения.
- Ограничения одного прохода: около 25 секунд, 250 000 записей файловой системы, 300 строк отчёта. API ограничивает время вызова 40 секундами и вывод 1 МиБ. Повторный старт — не чаще раза в минуту на процесс приложения. При ограничении выводится частичный отчёт, а не утверждение об отсутствии кандидатов.
- Символические ссылки не обходятся, отдельные файловые системы внутри релиза не сканируются. Отсутствующая/нечитаемая информация о защищённых релизах отключает кандидатов среди релизов. Если нельзя проверить процессы, оценка кандидатов отключается также для логов.
- Пользовательские документы, БД, резервные копии, системный journal, кэши npm/Prisma и произвольные каталоги не сканируются на очистку. Их политики хранения требуют отдельной настройки. Служебные пути сейчас фиксированы под существующую схему сервера; при другом размещении нужна адаптация root-скрипта.
- Служебная команда не запускает PM2 и не перезапускает приложение. Единственный создаваемый ей файл — пустой `disk-scan.lock` для координации проверок.

Если root-команда ещё не установлена, показатели свободного места остаются доступны; кнопка проверки покажет инструкцию о недоступной службе.

## Проверка обновления

```bash
python3 -m unittest discover -s tests/disk -v
npx tsx --test tests/disk/disk-api.test.ts
```

Тест API использует тестовые сеансы, подменяет запуск внешней команды и аудит; sudo и очистка в тесте не запускаются. Python-тесты работают только во временных каталогах.
