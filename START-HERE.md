# Space: отдельные версии и личные сообщения

Пакет подготовлен по архиву MyPlatform(1).zip. Это обновление исходников, не готовая
.output. Архив не содержит ключей, .env, зависимостей или файлов пользователей.

## Что изменилось

- Кнопка «Сообщения» в правой части подвала, счётчик непрочитанных.
- В модальном окне: диалоги / пользователи online, поиск по имени или логину,
  история, текстовое поле. Пользователю offline тоже можно написать.
- Все ACTIVE-пользователи, в том числе внешние, могут общаться друг с другом.
  Существующие диалоги с отключёнными пользователями остаются в истории, новые
  сообщения им запрещены. Администратор через API не получает чужую переписку.
- Текст до 4000 символов; Enter отправляет, Shift+Enter добавляет строку. Текст
  отображается как текст, без HTML. После неопределённого сетевого сбоя повторяется
  тот же запрос с тем же UUID, чтобы избежать дублирования.
- История хранится в PostgreSQL: chat_conversations, chat_members, chat_messages.
  Указатель прочтения отдельный для каждого участника. Сообщения прочитаны, когда
  диалог открыт, вкладка активна и пользователь дошёл до последних сообщений.
- WebSocket передаёт только адресные уведомления об изменениях. Содержимое клиент
  получает через API с проверкой сессии, активности и участия в диалоге. После
  переподключения и каждые 15 секунд в видимой вкладке выполняется сверка с БД.
- Группы, вложения, редактирование/удаление сообщений и автоматическая очистка
  истории пока не включены. Срок хранения не ограничен; включите таблицы чата
  в существующую политику резервного копирования PostgreSQL. Это не сквозное
  шифрование: администратор самой БД технически имеет доступ к сохранённому тексту.

## Перед первым развёртыванием

1. На компьютере разработчика перенесите файлы пакета поверх актуального проекта.
   prisma/schema.prisma основана именно на присланном архиве; если после отправки
   архива добавляли модели, объедините изменения, не затирая их.
   Старый deploy/websocket/ecosystem.websocket.cjs больше не используется; вместо
   него в пакете ecosystem.websocket.config.cjs с правильным окончанием имени.
2. В package.json исправлены build:ws/start:ws. В nuxt.config.ts убран встроенный
   пароль сессии: действующий NUXT_SESSION_PASSWORD берётся из серверного env.
   Сам серверный ключ НЕ меняйте, чтобы сохранить сессии пользователей.
3. В присланном архиве нет package-lock.json. Если в вашем Git он уже есть, сохраните
   его. Иначе один раз создайте файл на компьютере разработчика:

```bash
npm install --package-lock-only --ignore-scripts
```

   Проверьте изменения зависимостей и добавьте package-lock.json в Git вместе с
   исходниками обновления. Скрипт использует npm ci и без lockfile останавливается.
   Сохранение lockfile делает следующие сборки воспроизводимыми.
4. Отправьте commit в GitHub. На сервере обновите рабочую копию от обычного владельца
   репозитория (как делаете git pull сейчас):

```bash
cd /var/www/html/MyPlatform
git pull --ff-only
```

   Исходники должны быть закоммичены; скрипт не включает незакоммиченные изменения.
   Существующие .output и node_modules в рабочем каталоге не удаляйте и не собирайте
   поверх них: они пока нужны работающим процессам и первому откату.
5. Установите управляющий скрипт под root:

```bash
install -o root -g root -m 750 \
  /var/www/html/MyPlatform/deploy/releases/space-release.py \
  /usr/local/sbin/space-release
```

   Каталоги /var/www/space и /var/www/space/releases уже созданы. Скрипт сам создаёт
   каталоги версий и ссылку current. Python 3.12+ и стандартные sudo, git, npm нужны
   на сервере. Все команды space-release ниже выполняются под root.

## Настройки окружения

Используется существующий /etc/space/space.env (root:space, 640):
NUXT_SESSION_PASSWORD, WS_AUTH_SECRET, WS_ALLOWED_ORIGINS, DATABASE_URL и настройки
AD/почты/хранилища. Ключи должны быть не короче 32 символов.

Продакшен-секреты не передаются сборке. scripts/start-space.mjs перед импортом
Nuxt переносит существующие AD_URL, AD_DOMAIN_USERS, AD_USERNAME, AD_PASSWORD,
AD_TIMEOUT в соответствующие NUXT_AD_* переменные. Явно заданные NUXT_AD_* имеют
приоритет. FILE_STORAGE_PATH также поддержан. REDIS_URL применяется при запуске.
NUXT_ADMIN_LOGINS и NUXT_SMTP_* уже являются runtime-переменными и сохраняются.

Логи приложения вынесены в /var/log/space (создаётся при первом переключении).
Загрузки, ZIP-выгрузки и журнал файловых операций остаются в /var/www/uploads-storage.
Никакие данные пользователей не копируются в каталоги версий.

## Подготовка первой версии — без остановки приложения

```bash
space-release prepare
```

Скрипт берёт ровно текущий Git commit из /var/www/html/MyPlatform и создаёт, например:
/var/www/space/releases/20261007T190000Z-a1b2c3d4e5f6

Далее под пользователем space: npm ci --include=dev, prisma generate,
npm run build:ws, npm run build. При сборке лимит V8 — 4096 МиБ (как в предыдущем
обновлении); оставьте запас RAM для работающего приложения. Сборка потребляет CPU
и память, хотя не меняет действующую версию. Второй Nuxt не запускается.

При успехе выводится **READY: <ID>**. Запишите фактический ID: далее вместо RELEASE_ID
нужно подставить именно его. При ошибке продолжает работать старая версия; не
используйте незавершённый каталог. Скрипт не удаляет такие каталоги автоматически.

## Миграция чата

Сначала сохраните резервную копию БД своим обычным способом (например, PGAdmin).
Проверьте список ожидающих миграций:

```bash
space-release db-status RELEASE_ID
```

Команда Prisma status возвращает ненулевой код, если есть неприменённые миграции:
это ожидаемо перед установкой. В этом пакете новая миграция —
20261007190000_personal_chat. Если есть другие ожидающие миграции, проверьте их
содержимое: migrate deploy применяет ВСЕ ожидающие миграции проекта.

```bash
space-release migrate RELEASE_ID
```

Миграция чата только добавляет три таблицы; существующие таблицы и данные не
переписывает. Она совместима со старой версией приложения. Откат кода не удаляет
новые таблицы или сообщения. Не используйте migrate reset / db push для обновления.
Если Prisma сообщает о несовпадении истории миграций, остановитесь на этом этапе,
не переключая версию; действующее приложение продолжает работать.

## Переключение — короткий перерыв

После READY и успешной миграции:

```bash
space-release activate RELEASE_ID --db-compatible
```

--db-compatible означает, что вы проверили совместимость схемы со старой и новой
версией; скрипт не может автоматически определить смысл произвольной SQL-миграции.
Для миграции чата в этом пакете изменения добавочные и откат кода допустим.

Скрипт:
- сохраняет настройки двух текущих процессов (без дампа секретов окружения);
- атомарно меняет current;
- заменяет определения только space-app и space-ws, запускает их под space;
- проверяет readiness Nuxt (включая доступ к таблице чата) и WS, а также ID версии;
- сохраняет новый список PM2 для автозапуска;
- при неудаче пытается восстановить предыдущие процессы и current.

Два экземпляра Nuxt одновременно не запускаются: фоновые задания не дублируются.
Это НЕ zero-downtime: пользователи увидят короткий перерыв при запуске новой версии.
При ошибке запуск/возврат может занять дольше обычного перезапуска.

PM2 получает физический путь версии, на которую указывает current. Это намеренно:
он не должен сохранять устаревший cwd после переключения символической ссылки.
Актуальная генерируемая конфигурация находится в /var/www/space/runtime.json.
Старые /etc/space/ecosystem*.cjs после перехода не запускайте: они ведут в прежний
рабочий каталог. Автозапуск systemd по-прежнему восстанавливает сохранённый список PM2.

Текущий nginx менять не нужно, если /, /api и /_nuxt проксируются на порт 3000,
а /ws — на 5050, как в ранее настроенной конфигурации. Внутренний /internal/chat
WebSocket-сервера НЕ публикуйте через nginx: Nuxt обращается к нему по loopback.

## Проверка после переключения

```bash
space-release status
cd /home/space
sudo -u space -H /usr/local/bin/pm2 list
sudo -u space -H /usr/local/bin/pm2 logs space-app --lines 40 --nostream
sudo -u space -H /usr/local/bin/pm2 logs space-ws --lines 40 --nostream
curl --fail http://127.0.0.1:3000/api/public/health
curl --fail http://127.0.0.1:5050/health
```

Проверьте вход через AD, реестр, открытие файлов. Обновите страницу в двух разных
учётных записях: кнопка «Сообщения» в подвале, отправка в обе стороны, счётчик при
закрытом диалоге, «Прочитано» при открытии. Выйдите второй учётной записью, отправьте
сообщение и войдите снова — история и непрочитанные должны сохраниться.
Проверьте закрытие/повторное открытие модального окна, вторую вкладку и временный
обрыв WebSocket. Произвольный третий пользователь не должен читать чужой диалог.

## Следующие обновления

```bash
cd /var/www/html/MyPlatform
git pull --ff-only
space-release prepare
```

При изменении схемы — backup, db-status и migrate готового RELEASE_ID.
Затем activate RELEASE_ID --db-compatible. На сервере не нужно отдельно вызывать
build / pm2 restart / pm2 save: эти действия уже выполняет скрипт.
Если изменился сам space-release.py, сначала переустановите его командой install.

## Откат и восстановление

```bash
space-release rollback --db-compatible
```

Возвращает предыдущую конфигурацию процессов и ссылку, но НЕ откатывает БД.
Первый откат возвращает процессы в /var/www/html/MyPlatform: сохраните прежнюю
.output, dist-server и node_modules там до завершения проверки первой версии.

Если SSH/сервер оборвался во время переключения, журнал pending-switch.json остаётся.
Следующее переключение блокируется до восстановления:

```bash
space-release recover
```

Если автоматическое восстановление тоже не прошло, скрипт оставляет журнал и
сообщает об ошибке. Тогда проверьте PM2 и логи; не удаляйте журнал вслепую.

Старые и неудачные версии не удаляются автоматически. Пока не удаляйте каталоги,
на которые ссылаются current, текущие/предыдущие процессы или deployment.json.

## Проверки пакета

В среде разработки выполнены: полная production-сборка Nuxt, сборка WS, vue-tsc;
тесты авторизации WS и адресности уведомлений; проверки БД через Prisma на отдельном
PostgreSQL-совместимом PGlite (миграция, участники, идемпотентность, read cursor,
отключённый получатель); клиентский тест повтора отправки и загрузки пропущенных
сообщений; шесть изолированных тестов переключения/отката и тест runtime-настроек.

PGlite не заменяет проверку конкурентных транзакций на вашей версии PostgreSQL.
Тесты PM2 используют имитацию процессов: переключение на вашем сервере ещё не
выполнялось. Реальные AD, nginx, системные права, отображение в браузере и почта
проверяются после развёртывания. Дополнительные тестовые пакеты НЕ нужны production.
